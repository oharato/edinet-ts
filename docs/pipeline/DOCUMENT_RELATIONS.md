# 書類の親子関係と、一覧情報の変化を確認する

書類一覧に記載された親子関係と、観測ごとの状態変化を整理します。訂正版を選ぶ前に、親の未収録や循環などの確認点を調べるためのAPIです。

実装時の記録: 実装・ローカル検証済み（main統合前）。取得・DB更新・最新版の自動選択は行いません。

訂正や取下げを調べる際は、書類番号だけでなく、いつの一覧で何が報告されたかを残す必要があります。この機能は利用者が渡した一覧情報だけを読み、親として記載された書類と、同じ書類についての複数の観測を整理します。「観測」は、ある時点の一覧に載っていた情報1件です。

## 自動判断しないこと

`parentDocID`は、訂正報告書だけに使う項目ではありません。変更報告、追補、確認書、公開買付関連、取下書などにも使います。親番号がないことから、最初の原本とも断定できません。親が入力にない場合は「今回の入力に未収録」と扱い、存在しない書類とは判断しません。

同じ書類番号が複数の日の一覧に出る場合があります。`docInfoEditStatus`は一覧情報の修正に関する区分で、財務数値を訂正した書類かどうかを表す区分ではありません。親番号や提出日時などの情報が修正されても、原本自体は同じことがあります。異なる観測を保持し、最後の入力を最新版として採用しません。

| 一覧の項目 | 区分の意味 |
|---|---|
| `withdrawalStatus` | 0: その他、1: 取下書、2: 取下げられた書類 |
| `docInfoEditStatus` | 0: その他、1: 情報修正の通知、2: 情報修正された書類 |
| `disclosureStatus` | 0: その他、1: 不開示開始の通知、2: 不開示中、3: 解除の通知 |

0は「最新版で有効」という保証ではありません。親の状態を子へ自動伝播させたり、同じ会社や期間だけを結び付けたりしません。入力内の関係に循環が見つかっても、複数時点の観測を重ねた結果かもしれないため、確認候補として説明します。

## 公式仕様との対応

根拠は金融庁の[EDINET API仕様書 第2版（2026年6月）](https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf)です。印刷ページとPDFページは異なります。

- 区分値: 印刷47–48ページ、PDF52–53ページ。
- 取下げ後の項目と親子の例: 印刷59–63ページ、PDF64–68ページ。
- 原本を変えない一覧情報修正: 印刷64–66ページ、PDF69–71ページ。
- 親番号を使う書類の種類: 印刷87ページ、PDF92ページ。

原本を取得して照合する機能、訂正履歴全体の解決、検索用の財務DB移行は別工程です。現在の取得APIが持つ書類選択条件や、既存SQLiteの構造は変更しません。

## 入力と利用例

一覧のJSON応答全体をそのまま渡す形式ではありません。比較したい各行に、利用者が重複しない`observationId`（観測番号）を付けます。`listDate`は任意の一覧日です。以下は実書類を含まない合成例です。

```json
[
  { "observationId": "a", "listDate": "2025-06-30", "document": {
      "docID": "SYNTHETIC-A", "parentDocID": null, "withdrawalStatus": "0",
      "docInfoEditStatus": "0", "disclosureStatus": "0"
  } },
  { "observationId": "b", "listDate": "2025-07-01", "document": {
      "docID": "SYNTHETIC-B", "parentDocID": "SYNTHETIC-A"
  } }
]
```

```ts
import { analyzeDocumentRelations, DocumentWithdrawalStatus } from "edinet-ts";
const result = analyzeDocumentRelations(observations);
console.log(result.relations, result.diagnostics);
// 区分は DocumentWithdrawalStatus.Other などの定数でも指定できます。
```

APIは明示された観測を返し、書類番号ごとの観測一覧、親への参照、確認すべき点を整理します。親の参照先は「入力に未収録」「1観測」「複数観測」「自己参照」を区別します。診断は修正後原本の選択指示ではありません。項目が省略されていた場合と、明示的なnull、既知の区分値は分けて扱います。

```sh
npm run build
node dist/cli.js explain-document-relations --file /tmp/local-observations.json --pretty
```

CLIは2MiB以下の通常JSONファイルだけを読み、JSONを標準出力へ返します。入力不正は内容を転載しない定型メッセージと終了1、説明を返せた場合は終了0です。終了0は「最新版を確定できた」という意味ではありません。診断も確認してください。入力ファイルは変更しません。

これは手元の明示入力の確認機能です。ネットワーク取得、フォルダ走査、原本・既存DBへの書き込みは行いません。元の一覧にある説明文など、分析に使わない追加項目は読み取らず、出力にも保存しません。元のJSON自体を保管する必要がある場合は、別に保持してください。

## 上限と検証

> 以下は各検証を実施した時点の記録です。件数・配布先・未確認範囲を含めて読み、現在の稼働状態とは分けてください。

APIは観測10,000件以下、親参照先の観測ID合計100,000件以下に限定します。同じ書類の観測が多数あると、一つの親参照にも多くの観測候補が付くためです。

超過は途中の説明結果を返さず拒否します。CLIにはこれに加えて入力2MiBの上限があります。

上限超の一覧を、関連が失われることを隠して分割する機能はありません。必要なら、比較したい関係を利用者が明示して選び直してください。

合成入力で通常の親子、親未収録、同じ書類の複数観測、区分値、nullと未記録、自己参照、循環候補、入力不変、getterの一回取得、上限境界を検査しました。独立レビューでは到達関係を別に計算した1,535確認と、上限・入力固定の11確認が成功しました。

既存の実書類一覧の履歴を取得・照合した検証ではありません。原本の正しさ、訂正履歴全体、全市場での性能は未検証です。

Node26.12.1/npm12.2.1で全2,007テスト（既存1,952＋API52＋CLI3）、本体・利用例の型検査、build、保存保護Python5件が成功しました。lint設定はありません。入力上限や採用規則を緩めるための既存テスト変更はしていません。

公開ビルドの独立確認はESM/CJS各1,557項目（計3,114）、built CLI4項目が成功しました。CLI入力ファイルも不変でした。
