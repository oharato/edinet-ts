# 保存した2つの解析結果の違いを見る

同じ原本を解析した2つの保存結果を比較します。金額の差、表記の差、採用状態や出典の差を分け、比較できない場合はその理由を返します。

状態: main `ecb6c66`（#34統合済み）を基準に、この版で追加する読み取り比較機能です。未リリース。2026-10-24更新。

同じ原本を別の解析版で読み直したとき、流動資産・流動負債・負債合計について、**数値、採用状態、元の数値表記、出典、候補の記録**のどこが変わったかを説明します。流動比率も既存の厳密な分数で比較します。原本の再取得や再解析自体は行わず、保存済みの2つのIDを指定して読み取るだけです。

## まず端末から確認する

[差分取り込み](FINANCIAL_INCREMENTAL_IMPORT.md)の結果JSONに含まれる`snapshotIds`から、比較元と比較先を一つずつ選びます。解析版の文字列や提出日から新旧を自動判断しません。

Node26.12.1以上でリポジトリをbuildした後、次の形で実行できます。`BEFORE_ID`と`AFTER_ID`には保存結果の64桁IDを設定してください。

```sh
node dist/cli.js diff-bs --db /tmp/bs-input/financial.sqlite --before "$BEFORE_ID" --after "$AFTER_ID" --pretty
```

出力はJSONです。`summary`と`issues`が平易な説明、`metrics`が項目別の詳細です。`before`と`after`は入力した順番であり、日付順や正誤の判定を表しません。

- `changed`: 財務値・表記・採用状態・理由・出典・候補、または比率の計算結果に変化あり。
- `unchanged`: それらに変化なし。解析版だけ違う場合もここに入り、`provenanceChanges`に別途示します。
- `incomparable`: 対象が揃わず比較不可。`issues`に理由を返します。記録の単純な違いは見られますが、再解析による財務変化とは判断しません。

比較できればchanged/unchangedとも終了コード0です。比較不可は説明JSONを返して1、不正/不明ID、破損、DB入力エラーは標準エラーへ理由を出して1で終了します。変更を見つけたこと自体はコマンドの失敗ではありません。

## 何を比較できるか

会社コード・書類ID・対象日・連結/単体・会計基準・通貨・原本SHA256が同じで、採用値のentity（対象企業の識別情報）も両方で確認できて一致する必要があります。今回は日本基準・円だけです。別の原本や訂正書類を自動的に同じものとして扱いません。

両方とも全項目が欠損など、採用値から対象企業を確認できない場合は、会社名を推測せず比較不可にします。ただし元の欠損状態や理由はJSONへ残します。1項目が欠損でも、他の採用値から同じ対象企業を確認できれば、その項目の採用状態の変化は説明できます。

会社コード・会計基準・原本ハッシュ・解析版は保存時の宣言です。この機能が企業コードと公式原本の対応やハッシュの真正性を証明するわけではありません。同一原本の再解析を対象にしており、訂正/取下げの自動判断、異なる年度の成長率、どちらの版が正しいかの判定は行いません。

## 数値の差と出典の差を分ける

各項目の`valueComparison`は次の意味です。

| 値 | 意味 |
|---|---|
| `equal` | 両方の採用値が数値として同じ |
| `changed` | 両方の採用値が数値として違う |
| `unavailable` | 欠損・未対応・曖昧等で、両方に採用値/計算値が揃わない。0へ補わない |
| `not-comparable` | 会社や原本などが揃わず、数値を比較しない |

金額は元の十進文字列を正規化して等値を判定します。`00120.00`と`120`、`-0`と`+0.0`は数値として同じですが、`changes.raw`に表記の違いを残します。

numberや64bit整数へ変換しないため、巨大整数の差や小数の末尾も丸めて消しません。差額・増減率は計算しません。

不安全なraw値を比較できても、検索や比率計算へ安全なnumberとして採用できる意味ではありません。

`changes`では、`raw`（原文表記）、`status`（採用状態）、`reason`（理由）、`source`（採用元の情報）、`evidence`（候補の記録）、`numberAvailability`（安全なnumberの有無）を分けます。これらは複数同時に変わり得ます。

採用元の比較からrawと採用理由を分離しているため、数値変更をそれだけで「出典変更」としません。タグ・名前空間・context・対象期間・entity・単位・報告精度`decimals`等の変化は出典の変化です。候補にはrawや理由も含むため、数値変更と候補変更が同時に出る場合があります。候補の順序だけは無視し、重複の数は保持します。

## 流動比率とゼロ・欠損

`currentRatio`には両方の計算状態・理由と、計算できた場合の小数値/正確な分子分母を返します。小数1=100%です。等値判定には既存のBigInt分数比較を使い、表示numberが同じでも異なる分数を区別します。`1/3`と`2/6`は同じ比率です。

分母0、負値、欠損、曖昧、不安全な入力/結果は既存の計算不可状態を維持します。両方とも計算不可だから等値とすることはありません。計算不可の理由が変わったかも別に返します。原数値の報告精度を高める計算ではありません。

## プログラムから使う

```ts
import { BalanceSheetSqliteStore, compareBalanceSheetVersions,
    BalanceSheetDiffStatus, BalanceSheetValueComparison } from "edinet-ts";

// 停止済み試験DBのコピーを使います。
const store = new BalanceSheetSqliteStore("/tmp/test-copy.sqlite", { readOnly: true });
try {
    const result = compareBalanceSheetVersions(store, beforeId, afterId);
    if (result.status === BalanceSheetDiffStatus.Incomparable) console.log(result.issues);
    if (result.metrics.currentAssets.valueComparison === BalanceSheetValueComparison.Changed) {
        console.log(result.metrics.currentAssets.summary);
    }
} finally { store.close(); }
```

`store.getMany(ids)`は同じ読み取り時点でID群を検証して返します。不正・不明ID、保存破損があれば全体を拒否し、同じIDを2回指定することもできます。比較APIはこれを使い、比較途中の他接続更新を混ぜません。

比較APIは財務行を保存・変更しません。ただし、利用側がSQLite接続を開く際はreadOnlyでもWAL用副ファイルが作られることがあります。元フォルダまで変更したくない場合は、コピーを渡すか下記の保護を行うCLIを使ってください。

## 元DBの保護と確認範囲

`diff-bs`は#34の読み取り保護を共用し、通常ファイルの停止済み試験DB（最大256MiB）を一時コピーして、そのコピーだけをSQLiteで開きます。元DBや元フォルダを変更せず、missing DBも作成しません。

DB symlink・既存のjournal/WAL/SHM副ファイル・空ファイル・別用途DBは拒否します。実行中に元DBを変更しないでください。

利用中DBのオンラインバックアップではありません。

合成した旧解析/新解析のテスト用データを中心に、十進表記・巨大整数・出典のみの変更・採用状態・欠損≠0・分母0・等価/異なる分数・混在拒否・破損・読み取り時点・CLI終了コード・cold WALの元ファイル保護を検証しました。テスト用データの共有原本ハッシュは、同じ原本に対する旧版/新版の抽出結果を模した宣言で、実際の企業データを使った比較ではありません。

性能測定、新しい実原本の照合、全市場、訂正全履歴、本番移行、定期実行、PL/CF・他基準は対象外です。原本やDBはGitへ含めず、新規取得・追加依存・DB形式変更は行いません。
