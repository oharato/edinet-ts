# 実際の決算書と数値を照らし合わせた結果

確認日: 2026-10-23（UTC）。基準: mainの`b03d4a7054a5039dda6a77b74e326ad04943f216`。この記録と文書修正はローカル保持で、公開・リリースはしていません。

## 何が確認できたか

エクシオグループとミライト・ワンについて、2025年・2026年3月末の連結の流動資産・流動負債・負債合計を調べました。保存済みXBRLから読んだ**12項目すべて**が、会社の公式掲載PDFの表示値を円へ換算した値と一致しました。

両社を同じ日付で検索し、条件での絞り込み、金額順、ページ指定も確認できました。補助確認として、任天堂の2023年・2024年3月末の6項目も公式PDFと一致しました。今回の範囲で実装修正が必要な不一致は見つかっていません。

これは**3社・各2時点に限った確認**です。市場全体の品質を確認した結果ではありません。また、各社の後年の有報に掲載された「当期・前期」の比較列を使っており、前期当時に提出された別の有報との照合はしていません。

[用語集](GLOSSARY.md)では、連結・会計基準・対象日・XBRL・抽出根拠などを説明しています。

## 完全一致・丸め差・不一致の区別

- **完全一致**: XBRLの元の数値文字列と、「PDFの直接表示値×表示単位の円換算倍率」が同じ。今回の18項目はすべてこの結果でした。
- **丸め差の候補**: 差が表示単位より小さくても、自動で一致扱いにはしません。資料に書かれた切捨て・四捨五入の規則と、XBRLの精度指定を確認する必要があります。今回はこの判定を使った項目は0件です。
- **不一致**: 単位や丸め方を確認しても説明できない差。今回の対象では0件でした。

ミライト・ワンと任天堂の有報では、表の丸め方を明示した記述は確認できませんでした。エクシオ本文には百万円未満切捨ての記述がありますが、貸借対照表全体に適用する指定とまでは確認していません。今回は表示値との完全一致なので、特定の丸め規則を仮定していません。

表示値との一致は、百万円未満の実際の金額まで一致した証明ではありません。`decimals`は精度を示す属性で、値をさらに100万倍する指定ではありません。

## 複数社の検索で確認したこと

エクシオとミライト・ワンの実書類から、2025-03-31用と2026-03-31用の2つの集合を別々に作りました。各集合は実2社・同日・連結・日本基準・円です。入力の証券コード・基準・決算日も保存書類の記載と照合しました。

期待する結果は、PDFから独立に読んだ表示値を基準に決めました。各年25件、合計50件が成功しています。

ビルド済みCLIでも、実書類コピーを使う通常検索・条件検索・ページ指定・0件表示を両年で実行し、対象日の混在拒否と曖昧な値の除外も含めて10件が成功しました。

通常の2社検索では、各年とも2社が比較可能で、読めない値による除外は0社でした。年度をまたいだ比較ではなく、同一日の各社比較を2回確認しています。

## 読めない値を0にしないことの確認

実際の保存書類を使い、以下の5件も成功しました。表示金額の一致確認とは別の、入力・除外の確認です。

1. 保存済みラクーンの書類には同じ対象の負債合計候補が重複しているため、`ambiguous`（一つに決められない）を維持。3項目を必要とする検索では1社を理由付きで除外しました。この結果はすべての同社書類が曖昧という意味ではありません。
2. エクシオの保存有報に含まれない2024-03-31を要求すると、3項目が`missing`となり、1社を理由付きで除外しました。会社の金額が0という意味ではありません。
3. 対象日が混じった検索入力を拒否しました。
4. この検索で未対応のIFRSを指定した入力を拒否しました。
5. 保存済みのIFRS書類（旧ヤフー）で3項目の選択を試すと、`unsupported-standard`（会計基準が未対応）になりました。IFRSの値を日本基準の値に置き換えていません。

## 保存した記録と再現方法

Gitへ入れない詳細記録には、入力のコピーとハッシュ、PDFのURL・ハッシュ・ページ・単位・表示値、元タグ・context・対象日・連結範囲・entity・通貨・decimals・元の数値文字列・候補と採用理由、差額（円）、検索条件と結果を保存しました。金融データやPDFをこのリポジトリへ追加しないため、ここには照合結果の件数と根拠の公開URLだけを記載しています。

再現時は次の手順を守ります。

1. mainの基準commitを独立した作業ブランチで使い、指定のNode 26.12.1 / npm 12.2.1でbuildする。
2. 既存XBRLのコピーと会社の公式PDFを、Git管理外に保存する。取得元・内容ハッシュ・取得日時を記録する。
3. PDFの対象日・連結範囲・単位・3つの合計行を先に記録する。XBRLの値からPDF値を作らない。
4. `createBalanceSheetSnapshot()`または`selectBalanceSheetMetric()`に、確認した基準・範囲・対象日を渡す。
5. `selected`の元の数値文字列を、PDF値の円換算と十進整数のまま比較する。`number`へ変換して丸め差を隠さない。
6. 同日2社を`screenBalanceSheetSnapshots()`とCLI `screen-bs`へ渡し、PDF基準の期待順・条件一致と比較する。読めない項目と、検索条件に合わない項目を区別する。

今回の基準commitでは、build・型検査・型の使用例・全489テスト・保存保護のPython 5件も成功しました。これは上記の実資料照合18項目・API検索50件・CLI 10件・境界5件とは別の既存テストです。lintの設定はありません。

## 何がまだ分からないか

- 2025年など、前期当時に提出した別の有報との一致。今回は後年の比較列で2時点を確認しただけです。訂正・組替え前後を追う確認も未実施です。
- 単体・IFRS・US-GAAP・銀行保険・外貨・他の決算月についての、PDF表示値との網羅照合。
- 全市場・全年度の充足率や、自動更新後も同じ品質を保てるか。
- 利用者が誤った会社・会計基準を指定した場合の、主提出者情報や企業マスターとの自動照合。

カカクコムの旧公式PDFも探しましたが、公式サイトの動的表示から旧資料のURLを確認できず、独立したPDF照合は未完了です。その不足を埋めるために新規認証・有料API・大量取得を行っていません。今回は既存キャッシュと企業公式の匿名公開資料だけを使いました。

次は、別年度の提出原本や対象業種を少しずつ増やし、同じ記録方式で確認する段階です。今回の範囲では、本体コードの修正は必要ありませんでした。
