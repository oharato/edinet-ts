# 取得用DuckDBの検証計画

2026-10-31。停止済みの `daily-financial-compressed-v2/2026-10-30/candidate/` の `archive.sqlite` と `source-job.sqlite` を読取専用で扱い、前後の全ファイルSHA-256一致を確認する。本番サービス・原本・公開世代・依存定義は変更しない。

## 対象と比較条件

- 原本7,445件（gzip圧縮BLOB）、一覧観測139,758件、取得状態7,449件、試行履歴117件。解析キャッシュは空のため、解析済みテーブルの容量・書き込みは今回の対象外。
- 元の2つのSQLiteを検証用1ファイルへまとめたものと、同じ全テーブル・全列・主キー・副索引を持つDuckDBを比較する。gzipは再圧縮せず、そのまま移す。
- DuckDB 2.0.0 / PyArrow 26.0.0。Pythonでのストレージ層比較であり、Nodeの現行取得API・XML解析・ネットワーク・アプリ独自の事前検査時間は含まない。
- DuckDBは1スレッド。保存・復旧はmemory_limit=512MB、全原本の逐次照合だけ1GB。SQLiteはDELETE journal・synchronous=FULL。主キー競合時は双方とも既存行を保持する。

## 検証項目

| 項目 | 手順・合格条件 |
|---|---|
| 容量 | 全データの取り込みとcheckpoint/close後に比較。Parquet中間ファイルはDB容量に含めず、転記時間は別に記録 |
| 保存内容 | 全テーブルの全行・全列が一致。全圧縮XMLを展開し、原本hashとの一致も確認 |
| 一件保存 | 実取得117履歴から100件を選び、原本・原本観測・取得状態・試行履歴を1原本ごとにcommit。各エンジン3回、順序を交互にする |
| 一括保存 | 同じ100原本を1transactionでcommit。SQLiteはexecutemany、DuckDBはArrowの一括INSERT。変換とcommitを含む |
| 中断復旧 | 8原本を確定後、次の4原本のcommit前/直後で子processをSIGKILL。再open時に8件/12件が正確に残ることを確認 |
| 再開・重複投入 | 中断後に最初の32件を2回投入し、原本・取得状態・履歴が欠損も重複もなく一致。close/reopen後も再確認 |

強制終了は検証用process・DBだけに限定する。OS再起動・電源断・ディスク故障・WAL破損・アプリ全体の復旧を保証する試験ではない。元DBに対して復旧処理は行わない。

再現: `uv run --with duckdb==2.0.0 --with pyarrow==26.0.0 python scripts/validate-duckdb-acquisition.py`。再実行は `--output-directory` に新しいディレクトリを指定する。既存結果は上書きしない。

証跡・検証用DB: `data/benchmarks/duckdb-acquisition-20261031/`（Git管理外）。実行スクリプト: `scripts/validate-duckdb-acquisition.py`。

## 全件照合で見つかった制約

- 全量転記後、memory_limit=512MBで `archive_contents` のBLOBを含めて全件ORDER BYすると、512 MiBの確保に失敗した。`first-attempt.json` に記録した。
- sha256のIN条件で8件に区切る読み出しは成功したが、予備測定で約1.3秒/8件となり、実行計画も逐次走査だった。この方式の全件照合は中断した。取得時の書き込み性能とは分けて扱う。
- 全件監査は、メモリ上限1GBでソートせず一度だけ走査し、原本hashごとに元SQLite・比較用SQLiteと照合する方式へ変更した。予備の読取だけの測定では7,445件・圧縮BLOB 1,277,772,039 bytesを約6.38秒で読めた。process最大RSSは約1.77 GiBで、DuckDBのmemory_limitはprocess全体の上限ではない。
- 容量移行中には一時退避ファイルが約2.1 GiBになった観測がある。最大値の連続監視ではないため、必要作業容量の保証値にはしない。DB以外にParquet中間ファイル、WAL、退避領域も必要。

最初の全量転記は完了しているため、失敗後は `--resume-built` で同じ検証DBを再利用した。再開時も全行を元の停止済みSQLiteと照合し、元DBの実行前後hashを検査する。最初の転記に要した全時間の構造化記録は失敗で未保存となったため、書込性能の判断には後続の独立した100原本×3回の測定を使う。

## 検証結果

全9テーブルの全行・全列が、元のSQLite・統合した比較用SQLite・DuckDBで一致した。全7,445原本のgzip展開後のhashも一致し、展開後のXMLは合計17,475,948,060 bytes。元2DBの前後SHA-256は不変。

| 対象 | 件数 |
|---|---:|
| 一覧観測 | 139,758 |
| 原本・原本観測 | 各7,445 |
| 取得状態 | 7,449（完了7,440・未提供9） |
| 試行履歴 | 117 |
| 解析キャッシュ | 0（今回の検証対象に実データなし） |

### 容量

| DB | bytes | MiB |
|---|---:|---:|
| 統合SQLite | 1,409,032,192 | 1343.76 |
| DuckDB | 1,341,665,280 | 1279.51 |

DuckDBは約4.8%（約64.2 MiB）削減。検索用DBで確認した約92%削減とは異なり、gzip圧縮済みXMLが大部分を占める取得用DBでは削減効果は小さい。原本の圧縮方式・内容共有・主キー・副索引を維持した比較。

### 書き込み

実際に追加取得した117件からdocID順に100原本を使用。圧縮XML合計4,934,496 bytes（約4.71 MiB）。書込前にメモリへ読み込み、原本・原本観測・取得状態・試行履歴の4表を同じtransactionで保存した。各3回の中央値。

| 保存方式 | SQLite | DuckDB |
|---|---:|---:|
| 100原本を1件ずつcommit | 318.6 ms | 1173.2 ms |
| 100原本をまとめてcommit | 18.0 ms | 71.2 ms |

一原本ずつ確定するtransactionの中央値はSQLite約2.54 ms、DuckDB約10.77 ms。今回の100原本保存ではDuckDBが約3.7〜4.0倍遅かった。一括化するとDuckDBでも100原本を約71 msで保存できた。

これはPythonドライバによるストレージ層の比較。ネットワーク・gzip生成・XML解析・Nodeの現行取得API・保存前のアプリ検査は含まない。全原本平均より小さい追加取得原本の標本であり、全形式・大型原本での速度保証ではない。SQLiteの現在の本番実装は原本/状態が別DBだが、今回はエンジンを公平に比較するため両方とも統合した4表を同じtransactionで保存した。

### 中断・復旧

SQLite/DuckDBの双方で、commit前・commit後の計4ケースが成功。

- commit前にSIGKILL: 未確定の4件は残らず、確定済み8件の原本・状態・履歴を保持。
- commit後にSIGKILL: 確定済み12件を保持。DuckDBでは186,268 bytesのWALがある状態から再open・復旧できた。
- 復旧後に最初の32件を2回投入し、原本・状態・履歴が重複せず、全列一致。再close/open後も一致。
- 再openと内容確認はSQLite約1〜6 ms、DuckDB約32〜49 ms。小さな復旧用DBの測定であり、1.3GB全体の復旧時間ではない。

これはDBエンジンのtransaction復旧・同内容再投入の検証。edinet-tsのジョブ制御・解析版管理・競合する異内容の拒否・日次サービス復旧を実装した試験ではない。電源断・ディスク故障・WAL破損は未検証。

### 判断

取得用DuckDBは原本・履歴を欠損なく保持でき、今回のprocess強制終了からの復旧も通過した。ただし、容量削減・書込速度を主目的にSQLiteから移す優位性は示せていない。採用するなら、解析済みテーブル・検索用DuckDBとの連携やエンジン統一を主な理由とする。

運用実装では、一件保存と一括化の使い分け、原本BLOBの一括ソート回避、全件監査用メモリ/一時容量の確保を組み込む。原本の全件照合は移行・構築検証のためであり、通常の検索APIで全XMLを読み出す構成にはしない。実行全体のprocess最大RSSは約1.84 GiB（Python・Arrow・照合処理を含む）。
