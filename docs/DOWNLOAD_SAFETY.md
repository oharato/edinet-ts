# ZIP取得と保存時の保護

状態: この変更で追加する入力・保存検査。`download()`と`fetchXbrl()`を対象に、通常ZIPの読み取りと異常時の保存保護を合成データで検証します。実際のEDINETから新たに取得したZIPや、全市場での互換性の確認ではありません。

## 利用者から見た変更

- 保存先の外へ出るパス、同じ保存名に重なる項目、リンクなどを含むZIPは、展開する前にエラーにします。
- 新規保存は同じ保存先の私有の一時フォルダで行い、すべての項目を読み終えてから書類フォルダを公開します。途中失敗で作った一時領域は片付けます。
- 既存の書類フォルダは、空や未完成でも上書き・置換しません。有効なキャッシュなら読み、危険または未完成なら理由を返して止まります。自動再取得へ切り替えて既存データを壊しません。
- `PublicDoc`というフォルダの中の`.xbrl`を優先します。以前はZIP取得時とキャッシュ読取り時で優先順が食い違う場合があったため、同じ規則にそろえます。同じ優先順位の候補は、`/`区切りの相対パスの文字列順で選びます。
- エラーへHTTP応答本文や、通信例外中のURL・APIキーを含めません。JSON/HTMLが返った場合も本文は表示しません。

公開メソッドの呼び方は変わりません。`download(docID, targetDir?)`は保存済みファイルのパス、`fetchXbrl(docID)`は本文を返します。後者のネット取得はメモリ上で行い、キャッシュへ自動保存しません。

## 上限と受け付ける形式

| 項目 | 上限・規則 |
|---|---|
| 圧縮応答 | 64MiB。HTTP bodyの実際のchunk量を数えます。Content-Lengthだけを信用しません |
| 1項目の展開後サイズ | 64MiB。宣言値と実際に展開した量の両方を確認します |
| ZIP全体の展開後サイズ | 256MiB。全項目の宣言合計を確認し、各項目の実サイズとの一致を確認します |
| 項目数 | 中央ディレクトリー10,000件以下、暗黙にできる親フォルダを含む保存treeも10,000件以下 |
| 名前の長さ | UTF-8でパス全体4,096byte以下、各要素255byte以下 |
| 書類ID | 英数字で始まる英数字・`_`・`-`の1〜128文字。空や不明値`unknown`は拒否 |
| 圧縮形式 | 通常のclassic ZIP、STOREまたはDEFLATE。data descriptor付きも対象 |
| 名前の文字コード | ASCII、またはUTF-8指定のある名前。名前を別表記へ差し替えるUnicode extra fieldは非対応 |

MiBは1,048,576byteです。上限を拡大する公開オプションは追加していません。内部テストだけで小さい上限を使い、巨大な圧縮爆弾を実行せず境界を確認します。

**ZIP64、分割ZIP、暗号化、未知の圧縮方式、自己展開ZIP、ローカル領域の未対応の空隙などは拒否します。** JSZipが扱えるZIPの全機能を、この保存入口も受け付ける意味ではありません。以前は通ったZIPがエラーになる場合があります。

## 名前と展開データの検査

JSZipは読込み時に`..`を正規化し、同じ名前の項目を統合します。その後の一覧だけでは元の問題を見落とすため、先にclassic ZIPの中央ディレクトリーと対応するローカルヘッダーを限定的に検査します。展開そのものには引き続きJSZipを使い、別のZIP実装や依存は追加しません。

`..`・`.`・空の要素、絶対パス、ドライブ指定、バックスラッシュ、制御文字、Windowsの予約名や末尾の点/空白などを拒否します。名前の重複、大小文字やUnicode正規化で重なる名前、ファイルとフォルダの衝突も検査します。シンボリックリンクや特殊ファイルは作成しません。

展開中はchunkのbyte数を数え、上限や宣言値を超えたら止めます。終了時には宣言したサイズとCRC32（内容の破損を確かめる検査値）を照合します。CRC32は署名や原本の真正性を証明するものではありません。

根拠: [JSZipの読込み仕様](https://stuk.github.io/jszip/documentation/api_jszip/load_async.html)、[streamの一時停止](https://stuk.github.io/jszip/documentation/api_streamhelper/pause.html)、[PKWARE ZIP形式仕様](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)。形式仕様は参照し、文面や外部実装コードは転載していません。

## 保存先と既存キャッシュ

`rootDir`とその祖先、書類のキャッシュ内は、シンボリックリンクではない通常のフォルダ・ファイルを使ってください。全treeを検査してからXBRLを選びます。リンクや特殊ファイル、`.xbrl`という名前のフォルダ、空または64MiB超のXBRLは拒否します。祖先にリンクがあるパスも拒否するため、OSや保存先の構成によっては従来の指定を変更する必要があります。

キャッシュ本文は上限を付けて読み、読取中の変化と不正UTF-8を検査します。BOMは元の文字列として保持します。不正なbyte列を黙って置換しません。

書類ごとの排他的なlockファイルと私有stagingフォルダを使います。既存書類フォルダが途中で現れた場合も止め、置換しません。他の処理が取得したlockを削除しません。失敗後に新しく作った空の親フォルダが残る場合がありますが、書類フォルダへ部分ファイルを公開しません。

**この保護は、同じ規則を守る処理と信頼できる保存先を前提にします。** 別のプログラムが検査と公開の間にパスを入れ替える敵対的な同時変更、プロセス強制終了、電源断、OSをまたぐ完全な耐障害性は保証しません。強制終了でlockや一時領域が残った場合、自動削除はせず利用者による確認が必要です。本番キャッシュの移行・修復・削除は行いません。

## 本文受信までの時間制限と中断

`requestTimeoutMs`を指定すると、1回の通信を開始してから本文を受け取り終えるまでに期限を付けられます。待ち行列や再試行までの待ち時間は、この期限に含めません。受信本文が止まった場合も対象です。**省略時は従来どおり無制限**なので、期限が必要な利用では明示設定してください。

```ts
import {
  EdinetXbrlDownloader, EdinetRequestError, EdinetRequestErrorCode
} from "edinet-ts";

const client = new EdinetXbrlDownloader({
  apiKey: process.env.EDINET_API_KEY,
  requestTimeoutMs: 30_000,
  maxRetries: 2 // 最初の1回に加えて最大2回、合計3回まで
});
const controller = new AbortController();
try {
  const documents = await client.search("2026-01-01", undefined, {
    signal: controller.signal
  });
  console.log(documents.length);
} catch (error) {
  if (error instanceof EdinetRequestError) {
    if (error.code === EdinetRequestErrorCode.Aborted) console.error("中断しました");
    else if (error.code === EdinetRequestErrorCode.Timeout) console.error("通信が時間切れです");
    else console.error("通信に失敗しました");
  } else {
    throw error; // HTTP状態や応答の不正などは別のエラー
  }
}
// 利用側が止めたい時に controller.abort() を呼びます。
```

`requestTimeoutMs`は1〜2,147,483,647msの整数です。これは1回ごとの期限であり、再試行を含む全処理の30秒保証ではありません。中断用の`signal`を使うと、待ち行列・通信中・再試行待ちでも利用側から止められます。任意の中断理由をログやエラーへ転載しません。

既存の引数と戻り値は保ち、次の末尾に省略可能な`{ signal }`を追加します。不要なら従来の呼び方のままです。

| メソッド | 中断指定の位置 |
|---|---|
| `search(date, typeFilter?, request?)` | 第3引数 |
| `download(docID, targetDir?, request?)` | 第3引数 |
| `fetchXbrl(docID, request?)` | 第2引数 |
| `searchPeriod(start, end, typeFilter?, request?)` | 第4引数 |
| `findLatest(ticker, type, lookbackDays?, request?)` | 第4引数 |
| `downloadByTicker(ticker, targetDir?, date?, type?, request?)` | 第5引数 |
| `Edinet.getFinancialHistory(ticker, years?, docType?, request?)` | 第4引数 |

`EdinetRequestErrorCode.Aborted`は利用側の中断、`Timeout`は設定した通信期限の超過、`Network`は通信障害です。HTTPの非成功状態、不正JSON、業務エラー、不正ZIPはこれらと区別して失敗を返します。エラー文面の一致より型と定数を使って判定してください。

### 再試行・後片付けと範囲

本文受信が終わるまでRateLimiterの枠を保持します。既定の並列数1が本文受信にも適用されるため、以前のようにヘッダーだけ受け取って次の本文受信を並行開始しません。期限未設定で先頭の本文が止まると、後続も待つ可能性があります。

呼出元の中断は再試行しません。通信障害・時間超過と429/5xxは、残り回数がある場合だけ再試行します。不要な本文を取り消し、最後の試行の後には待ちません。不正JSON・業務応答・不正ZIPの解釈を通信再試行の外に置きます。タイマー・signalのlistener・readerのlockを片付け、本文の取消し完了が返らなくても操作を永久待ちにしません。

この期限はJSON・ZIP本文の受信までです。**XML/ZIP解析、同期ファイル操作、キャッシュ保存、DB処理までを含む総時間や強制中断は保証しません。** JSON本文の新しい容量上限も今回追加していません。実APIの待ち時間・速度は測定せず、合成Response/ReadableStreamと仮の時計で確認します。本番側の設定、取得予定、認証、保存済みデータは変更しません。

標準APIの参照: [Node.js AbortController](https://nodejs.org/api/globals.html#class-abortcontroller)、[Fetch仕様](https://fetch.spec.whatwg.org/)、[Streams仕様](https://streams.spec.whatwg.org/)。

## サーバーが指定する再試行待ちと追加待ち

429または5xxの応答に`Retry-After`がある場合、次の通信まで待つ指定として扱います。対応する値は非負整数の秒数と、曜日付きGMTの現行HTTP日時形式（IMF-fixdate）です。日時は1900年以降で、曜日・日付・時刻が一致するものに限定し、過去日時の待ちは0にします。

```ts
const client = new EdinetXbrlDownloader({
  apiKey: process.env.EDINET_API_KEY,
  requestTimeoutMs: 30_000,
  maxRetries: 2,
  maxRetryDelayMs: 60_000
});
```

`maxRetryDelayMs`は**再試行1回の待ち上限**で、既定60,000ms、指定範囲1〜2,147,483,647msです。通信1回の期限`requestTimeoutMs`や、処理全体の所要時間とは別です。サーバー指定が上限を超える場合、自動再試行を止め、そのHTTPエラーを呼出元へ返します。指定時刻を早めて再送しません。例えば既定上限で`Retry-After: 120`なら、自動再試行を終了します。

| 指定 | 動作 |
|---|---|
| 有効な秒・現行日時で上限内 | 指定より早く再試行しない。独自待ちの方が長ければそちらを使う |
| 有効な指定が上限超、または非常に大きな整数秒 | 待たず自動再試行を終了し、HTTPエラーを返す |
| 旧式RFC850/asctimeらしい構文 | 解釈を推測せず、自動再試行を終了する。旧式日時の暦日を完全に検証する実装ではない |
| 現行日時の秒60（うるう秒） | JavaScript Dateで正確に扱わず、自動再試行を終了する |
| 空・負数・小数・指数表記・その他不正な値/日時 | 通常の指数待ちを使う |

**HTTP日時の全形式に対応した実装ではありません。** RFC 9110の受信側が求める旧式日時の解釈は未実装です。対応外の旧式らしい指定は、安全側に停止する限定です。[RFC 9110のRetry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)と[HTTP日時](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.7)を参照しています。

独自の指数待ちは1秒、2秒、4秒…を基礎に上限内とし、0〜25%の追加待ち（jitter）を余白内で加えます。再試行が同じ時刻へ集中するのを減らすためです。サーバー指定の方が長ければその指定が優先され、その場合の分散までは保証しません。最後の試行の後には日時の解釈・乱数取得・待機を行いません。

この変更で、設定省略時にも既定60秒の待ち上限とランダムな追加待ちが適用されます。従来の秒単位の決まった待ちと完全に同じ時刻にはなりません。中断signal・本文の取消し・通信期限・最大再試行回数・秘密情報非表示は維持します。HTTPヘッダー原文をログや例外へ出さず、実APIを使った待ち時間測定や本番設定の変更は行いません。
